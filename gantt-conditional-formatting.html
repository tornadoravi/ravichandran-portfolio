01 / Create Formatting Rule

A workload signal.
Not just a color choice.

Schedule Hours > 0 is the displayed condition. Rule 1 separates the qualifying metric from its targets and appearance.

Milestone Icon, Fill, Bar Fill, and Data Label have individual controls. The shown fill swatches are orange; the data-label swatch is black. Discard and Apply remain separate actions.

A positive-hours threshold identifies scheduled work, not over-allocation against capacity.

“Impacts On” shows Bar and a +2 indicator. “Apply To” includes Bar and a truncated second label. Hidden selections are not inferred.

Design rationale / Reading the supplied interface

Make the workload signal explainable.

Keep the metric, target, and visual treatment distinct. These are design trade-offs, not measured usability findings.

  1. 01

    Make the threshold readable.

    Field, operator, and value expose the rule in one row. Schedule Hours > 0 should not be presented as an overload alert: that needs a capacity-based criterion not shown here.

  2. 02

    Where does it apply?

    Impacts On and Apply To precede the rule. The trade-off is compactness: hidden selections and truncated labels need inspection before the full scope is clear.

  3. 03

    Keep values legible alongside color.

    Numeric summary labels retain meaning beyond the fill. Separate label styling provides control, but contrast and non-color cues still need validation; the screen alone does not establish accessibility.

Evidence & official product context

Resource formatting is documented.

Microsoft Learn's Customize resource layout guide documents formatting rules for task bars, summary bars, and milestones, including summary-metric conditions and Bar / Data Label targets. This supports the feature context—not a claim that every control or result in this design has been independently tested.

Scope, delivery & source limitations

My contribution: this case sits within the confirmed end-to-end PowerTable Gantt and resource UX/UI scope, including developer handoff and implementation review. It does not imply Microsoft employment or ownership of all production code.

Evidence: one supplied editing state, presented as three native-resolution crops: rule editor, resource metric toolbar, and timeline. They are not a before/after sequence. Surrounding resource names, account controls, and workspace chrome are excluded; no interface controls, colors, or values have been repainted.

Limits: hidden target selections, rule precedence, invalid-input feedback, save persistence, Apply/Discard behavior, and post-application results are not established by this screenshot. This is a screenshot-led design case, not an interactive rule engine.

Documentation versus design: the official Resource layout guide also describes AND/OR conditions and rule management; those states are not supplied here. Its Scheduled Hours > 8 example is separate from this design's Schedule Hours > 0 condition. Documented component choices do not reveal the selections hidden behind this screen's +2 indicator or truncated label.

Validation: no independently verified feature-specific review, usability finding, or business-impact metric is included. Public documentation supports the capability, not independent testing or the release status of this exact design. General grid formatting, Intelligence charts, and Analytics+ Gantt are not substituted as evidence.
